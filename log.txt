Prerequisites to run the project (the model is now part of startup):
1. Python 3.14 (what the project is built and tested on).
2. From the repo root, make the virtual environment and install the libraries:
   python3 -m venv .venv
   .venv/bin/pip install -r requirements.txt
   (installs numpy, pandas, paramiko, torch, transformers, accelerate)
3. At least 15 GB of free disk space. The model is Phi-4-mini-instruct from Hugging Face (microsoft/Phi-4-mini-instruct).
   It is NOT in the repo. It downloads itself (7.7 GB) the first time startup runs, so the first run needs internet and takes a while.
   No Hugging Face account or token is needed.
4. 16 GB of RAM recommended, the model takes about 8 GB while running.
5. Always run with .venv/bin/python, not plain python3, or the libraries will not be found.
   Run the tests (they use a stand-in for the model, so no download needed):
   .venv/bin/python -m unittest tests.test_msm tests.test_startup tests.test_sheet tests.test_flow
   Run the full system (details below):
   .venv/bin/python -m src.main

How to run the full system as it stands right now (fraud detection is the model's only job):
1. Put the csv files to check in purchase_data/. Each csv becomes one sheet, the file name is its id.
   Two layouts work: bank (Description, Date, Amount, Transaction_Type) and store (Date, Item, Amount (USD)).
2. From the repo root run:
   .venv/bin/python -m src.main
3. What happens, in order:
   - startup: manager goes stopped -> starting, loads every csv into a sheet, loads the model, then goes operational.
   - each sheet is sorted by date and vetted. a sheet with bad data (missing values, unreadable dates or amounts) is NOT checked, it prints "not checked, fix the data first".
   - the code shortlists the irregular purchases (one-off item at that price, amount 3x the usual, same charge twice in a day, 3+ charges in a day).
   - the model is asked about each shortlisted purchase one at a time and answers FRAUD or OK with a reason.
   - each flag is routed back to its own sheet and row.
4. What you see: the manager state ("operational"), then per csv the number of possible fraud and one line per flagged purchase (row, date, item, amount, reason).
   On my Mac the whole run takes about 80 seconds for the two csvs in purchase_data/. If startup fails it prints "startup failed: ..." and the state is "error".
5. To use it from code instead of the terminal (this is what the frontend will read):
   from src import main
   results = main.run()          # {sheet id: dashboard entry}, or None if startup failed
   results["data.csv"]["fraud"]  # the flagged purchases for that sheet
   Each dashboard entry has: sheet_id, person_name, banks, places, vet, analysis, irregular, fraud.
   The same entries are kept in managerdaemon.dashboard.
6. Not done yet: no frontend or API is connected, nothing is hosted on AWS, and steps 5-6 of the action plan (supervision, concurrent requests) are not started.
   The model's FRAUD/OK calls have not been checked against known fraud, treat them as "possible fraud".

Step 5 is done. We now log what it does, stops work when something breaks, tries to fix itself, and reports to us team if it cannot.
Also made it so if only one sheet breaks that only the things related to that sheet break. Everything else remains working. However
no failsafes run if its only one sheet thats broken. 

If its startup that failed however or every sheet breaks then it does the failsafe methods we previously discussed.
Below are the detailed steps of what happens.

What happens when something breaks
1. ONE sheet breaks (bad layout, error while checking it): only that sheet stops. Its dashboard entry gets an "error" field saying what went wrong and its fraud is empty.
   Every other sheet is still checked and the manager stays operational. No failsafes fire. The sheet is tried again from scratch on the next run.
2. Startup fails, or EVERY sheet breaks in the same run (so the problem is the system, e.g. the model): the manager goes down this ladder, trying the work again after each one:
   - report the error: logged with its traceback, manager enters error state, work stops (the state is checked before every sheet).
   - recovery: checks the data is still loaded and reloads the model if needed. (recover in managerdaemon)
   - failsafe 1, power cycle: initialize is recalled, so shutdown, reload the csvs and the model, start again.
   - failsafe 2, cry to dev team: writes the error, traceback, manager state and loaded sheets to logs/dev_report.txtl, prints a loud message, and leaves the manager in error state. (failsafe2 in managerdaemon)
   Heads up: with only one csv loaded, that one sheet breaking counts as "every sheet" and goes all the way to failsafe 2.

Important Files and stuff to know
- logs/manager.log: everything the manager does (state changes, sheets loaded, each sheet checked, errors with tracebacks). Read this first when something is off.
- logs/dev_report.txt: only exists if failsafe 2 fired.
- logs/ is in .gitignore, it is made on the first run.
- main.run() returns None if the run could not be fixed. Dashboard entries now have one more field: error (empty when the sheet is fine).
- Tests for all of this are in tests/test_supervision.py. Run every test with:
  .venv/bin/python -m unittest tests.test_msm tests.test_startup tests.test_sheet tests.test_flow tests.test_supervision
- To just run the program no tests (loads the csvs in purchase_data/, loads the model, and prints the AI's fraud replies):
  .venv/bin/python -m src.main
  prints the manager state, then for each csv the purchases the AI flagged as fraud with its reason

Not done in step 5:
- failsafe 2 only writes a file and prints. No alert yet, we decide where reports go later
- recovery cannot fix bad data or a code bug
- nothing watches in the background, errors are caught when an operation fails. errorcheck in msm is still the placeholder for a watchdog

Detailed Version of everything added for Step 6:
- Requests: anything done to a sheet goes through request in managerdaemon. Each sheet has its own queue, so two actions on the same sheet never run at once and they run in the order asked. Different sheets run at the same time.
  Example: MD.request("data.csv", Sheet.delete_cell, 0, "Amount").result()
  Calling a sheet's methods directly skips the queue, so always use request.
- All sheets are now fraud checked at the same time. It is not faster yet: there is one model and it can only answer one question at a time.
- Refresh (D_refresh in managerdaemon): compares the csv folder to what is loaded. New csv -> new sheet, changed csv -> sheet rebuilt, deleted csv -> sheet dropped. Only new and changed sheets are checked again.
  A csv that cannot be read is skipped and logged, and tried again only when the file changes.
- Stay up mode: runs everything once, then refreshes every 30 seconds until ctrl-c:
  .venv/bin/python -m src.main serve 30
  Plain .venv/bin/python -m src.main is still a single run.
- When an error is reported, anything still queued on any sheet is dropped and work already running finishes. A run that had an error reported during it fails and goes to supervision (step 5).
- Tests are in tests/test_requests.py. Run every test with:
  .venv/bin/python -m unittest tests.test_msm tests.test_startup tests.test_sheet tests.test_flow tests.test_supervision tests.test_requests
